# Pre-Print research readiness

## Local verification

Use the existing app on a loopback-only development server (`npm run dev -- --hostname 127.0.0.1`). Keep local environment files out of Git. On **Pre-Print Optimizer → Research printer and mix settings → Check research setup**, the two checks report independently:

- **Web research:** Set `AUTOBUILD_RESEARCH_OPENAI_KEY` in `.env.local` for local use or in the server-only environment for the deployment. `AUTOBUILD_RESEARCH_MODEL` is optional; the default is `gpt-5.4-mini`. Restart or redeploy after setting the key. Select **Check research setup**, then enter the exact printer and mix and select **Look up settings**. The setup check does not verify provider access or make a paid request. Do not put the key in chat or a `NEXT_PUBLIC_` variable.
- **Profile storage:** set `AUTOBUILD_PROFILE_STORE_PATH` to an absolute filename in an existing private, writable directory on the machine running Next.js. An existing file must be a readable v1 catalog. The check does not create or write it. Without this option, approved profiles may be stored in the current browser; unreviewed results are not persisted there. The local file is shared by browsers using that one development server, not by hosted instances or organizations. Do not use live customer data in it.

Use exact models and mix variants. A matching saved profile takes priority over a new search; the operator selects source-backed values before applying. Initial set and open time are distinct, 28-day strength is in MPa, and recommended mixing water is normalized to L/kg dry mix only from an explicit source dosage. All four are reference-only; none changes toolpaths or dosage. Use existing printer configuration when no research is available. Check original discovery dates; a new review does not refresh sources.

To reproduce the browser smoke test, use port `43731`, leave the key unset, set the model to `fixture-model`, point the catalog path at a new file inside an existing scratch directory, and set `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:43998` and `NEXT_PUBLIC_SUPABASE_ANON_KEY=local-smoke-only`. Once the route responds, run `python tests/pre-print-browser.py` in an environment with Playwright Chromium installed. The test uses an isolated browser, never calls the provider, and does not write to Supabase or the catalog file.

## Hosted private pilot

The page and research endpoint are closed by default. For the private, single-operator pilot, configure `AUTOBUILD_V1_PILOT_SHA256` as described in `docs/v1-release-access.md`. The research handler itself checks HTTPS, the pilot credential, and same-origin request metadata. Set an OpenAI project budget before using paid research; the handler's cooldown is per process and is not a durable quota. Hosted reuse is browser-only. The separate Python optimizer is not tested by the research setup check. The browser uses `NEXT_PUBLIC_API_URL` for scan/optimize; do not put the FastAPI secret in a public variable or expose the generic backend proxy to restore access.

Before expanding beyond the single-operator pilot:

1. Establish a verified server-side user session and resolve organization/project membership from stored authorization data. Apply the same authorization to the page, diagnostics, lookup, review, and research; grant review/research separately from read access. Never trust a client-supplied tenant, role or review timestamp. Host only over HTTPS with secure session cookies, same-origin mutation checks, and no-store responses. If optimizer access is needed, use separately authorized, narrowly scoped scan/optimize endpoints with server-only upstream credentials and upload limits.
2. Back the catalog with persistent tenant-scoped printer, material, and profile/finding records. Use foreign keys and a unique index on tenant + normalized exact printer/mix pair. Store field, canonical unit, source, discovery timestamp, provenance, revision, and review actor/time. Enforce tenant isolation on reads and writes in the database as well as the API. Keep production browser caches disabled or scoped to the authenticated tenant. Add manual edit/add as a separate reviewed write with explicit provenance, not as an AI finding.
3. Do the exact match lookup before any provider call. On a miss, atomically reserve one job per tenant/pair and enforce a durable tenant/user quota and global spending limit before dispatch. Keep a bounded timeout and return sanitized errors. Review by revision and server-stored finding IDs, rejecting stale changes atomically. Re-checking expired evidence should be an explicit action, not silently triggered by a lookup.
4. Before enabling access, verify anonymous denial on the page and API, cross-tenant denial, reviewer permissions, persistence after a restart, exact reuse from a second authenticated browser without a second provider call, and quota/concurrency behavior. Run a separately authorized provider smoke test and compare the browser's downloaded G-code from two controlled runs with different approved settings. Leave the production gate closed until these checks pass.
